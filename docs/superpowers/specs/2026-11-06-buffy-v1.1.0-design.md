# Buffy v1.1.0 — Wardrobe and Idle Life

> **Status:** proposed · 2026-11-06
> **Baseline:** v1.0.1 (`2cd1681`)
> **Target:** v1.1.0

## Why

Buffy already reacts well to agents, but she has only one look and one thing to do when nothing is happening. v1.1.0 makes her feel like a companion rather than a status indicator: a wardrobe with real choices, saved looks, and a small idle life of reading, coffee, and stretching.

Success looks like this: any look is two clicks away in a visual wardrobe, the overlay updates instantly, old wardrobe choices survive the upgrade, and a quiet desk gets a pet who reads a book or sips coffee without ever getting in the way of `needs-you`.

## What exists today

- `overlay/main.cjs` stores four values in `~/.buffy/wardrobe.json` — `bow`, `hat`, `wand`, `theme` — and exposes them through tray radio menus. It sends them to the renderer over IPC.
- `overlay/renderer.js` is a 1,752-line classic script. It draws the entire character procedurally on a 300×330 transparent canvas. Themes swap a palette object; the rest of the art is hard-coded draw calls.
- Idle is breathing and blinking. After 30 seconds without activity she enters `sleepy`, and she wakes on hover or click. There is no activity scheduler and no props.
- A hatched PNG (`sprite.type === 'image'`) replaces the whole body. The renderer skips every procedural layer, including accessories.
- `src/config.js` owns `config.json` defaults and exposes `writeConfig`. The overlay main process currently reads only `port` from the file.
- Tests are Node-only (`node --test`). The packaged smoke test checks `#stage`, `#sessions`, `window.buffy`, and `document.readyState`; there is no DOM test harness.

## Goals

- A wardrobe window with a live preview, browsable categories, mix-and-match outfits and accessories, and saved looks.
- More visual range: five outfits, five bow choices, four hats, four glasses, three wand styles, and six themes. Each accessory list includes a "none" option.
- Idle hobbies: reading, drinking coffee, and stretching. They play only when Buffy is idle, are interruptible, and are purely cosmetic.
- Existing v1 wardrobe files migrate without losing choices.
- The overlay, wardrobe window, and docs all agree on one character and one catalog.
- A clean v1.1.0 release with installers, updater metadata, and updated README/site/screenshots.

## Non-goals

- A color wheel, arbitrary patterns, per-layer color editing, or an import/export format. That is the v1.2 editor, not this release.
- User-uploaded outfit packs or third-party assets.
- Outfits or hobbies on hatched custom sprites. A hatched sprite remains a full-body replacement.
- New agent events, daemon states, XP, mood, or counters for hobbies.
- Cloud sync, accounts, or a mobile/web version.
- A new UI framework, bundler, or runtime dependency.

## Anti-goals

- Hobbies that delay, obscure, or replace `needs-you`, `working`, `thinking`, `error`, or `done`.
- A wardrobe that requires editing JSON to use.
- Losing a v1 bow, hat, wand, or theme during migration.
- Two sources of truth for the palette or catalog between the main process and the two pages.
- A wardrobe window that draws a different Buffy than the overlay.
- Shipping a window that does not fit a 1280×720 desktop.

## Constraints

- Electron with `contextIsolation`, `sandbox`, and a self-only CSP. No remote scripts or styles.
- `file://` pages cannot import ES modules in this setup, so shared browser code stays classic scripts loaded with `<script>` tags. No bundler.
- Node.js 20+ for source and CLI.
- Windows, macOS, and Linux builds; everything under `overlay/**` is packaged inside `app.asar` except `src/**`.
- Existing Node tests must keep passing. Visual correctness is checked with the `--shot` capture path and the packaged smoke test; there is no canvas assertion framework.
- The overlay window stays 300×330. The new window is a normal framed window.
- Local-only behavior and the existing privacy posture stay unchanged.

## Approaches considered

### A. Expand the tray menus

Add more bows, hats, outfits, and themes to the existing radio submenus.

**Trades:** smallest change and no new window, but 20+ items across nested menus with no preview is clumsy, and it makes the catalog hard to discover. It also keeps the renderer as the only place to see a choice. Rejected.

### B. Wardrobe window with curated presets — chosen

A framed 760×660 window with a live character preview, tabs for Looks / Outfit / Accessories / Theme, saved looks, and a "Surprise me" action. The existing procedural art stays, but the character drawing moves into a shared module used by both the overlay and the window. The tray menu shrinks to opening the wardrobe plus a random-look shortcut.

**Trades:** one focused refactor (extracting the character renderer) and a new window, but it gives the release a real feature, keeps the art consistent, and leaves room for the v1.2 editor. This is the best balance for a minor release.

### C. Full outfit editor

A color wheel, pattern picker, per-layer control, and import/export.

**Trades:** the most expressive, but it needs a larger schema, undo, validation, and an asset pipeline. It would dominate the release and delay the idle work. Deferred to v1.2.

## The design

### 1. Wardrobe model and catalog

`~/.buffy/wardrobe.json` moves to version 2:

```json
{
  "version": 2,
  "outfit": "princess",
  "bow": "none",
  "hat": "none",
  "glasses": "none",
  "wand": "none",
  "theme": "rose",
  "presets": [
    {
      "id": "6f0c…",
      "name": "Date night",
      "createdAt": "2026-11-06T21:00:00.000Z",
      "look": {
        "outfit": "starlight",
        "bow": "lavender",
        "hat": "none",
        "glasses": "star",
        "wand": "heart",
        "theme": "midnight"
      }
    }
  ]
}
```

The catalog is a plain CommonJS module, `overlay/wardrobe-catalog.cjs`, so the main process can require it, tests can import it, and the wardrobe window can receive it over IPC. It owns:

| Slot | Items |
| --- | --- |
| `outfit` | `princess`, `cozy`, `sleepover`, `rainy`, `starlight` |
| `bow` | `none`, `pink`, `lavender`, `mint`, `gold` |
| `hat` | `none`, `beret`, `party`, `sunhat` |
| `glasses` | `none`, `round`, `heart`, `star` |
| `wand` | `none`, `star`, `heart` |
| `theme` | `rose`, `lavender`, `mint`, `sky`, `butter`, `midnight` |

Three built-in looks live in the catalog: **Royal** (princess, pink bow, star wand, rose), **Cozy** (cozy, mint bow, round glasses, butter), and **Starlight** (starlight, lavender bow, star glasses, heart wand, midnight). Built-ins cannot be deleted. User presets are stored in `wardrobe.json`, capped at 12, with unique case-insensitive names of 1–24 characters.

The module also owns the pure operations:

- `normalizeWardrobe(raw)` — accepts v1 or v2 and returns a valid v2 object.
- `lookOf(wardrobe)` — the six cosmetic fields, for comparison and presets.
- `applyLook(wardrobe, look)` — returns a new wardrobe with a look applied.
- `addPreset(wardrobe, name, { id, now })` — returns `{ wardrobe, preset, error }`.
- `removePreset(wardrobe, id)` — returns a new wardrobe; built-ins are rejected.
- `findPreset(wardrobe, id)` — resolves a built-in or user preset.
- `randomLook(random)` — injectable randomness for tests and "Surprise me".

Normalization is the safety boundary: unknown slots, old values, malformed presets, and duplicate IDs fall back to defaults rather than crashing a renderer.

### 2. Wardrobe window

A standard framed `BrowserWindow`, 760×660, resizable down to 640×560, centered, with the title "Buffy's wardrobe". It uses the onboarding visual language: warm cream background, pink/lilac gradients, rounded cards, and the same system font stack. It loads `overlay/wardrobe.html`, `wardrobe.css`, `wardrobe.js`, and `wardrobe-preload.cjs`.

```
┌──────────────────────────────────────────────────────────────────┐
│  Buffy's wardrobe                                   [Surprise me]│
│  Dress her up. She keeps the look.                               │
├────────────────────────┬─────────────────────────────────────────┤
│                        │ [Looks] [Outfit] [Accessories] [Theme]  │
│      live preview      │                                         │
│       300 × 340        │  Outfit                                 │
│                        │  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│   [Idle] [Reading]     │  │Princess │ │  Cozy   │ │Sleepover│   │
│   [Coffee] [Stretch]   │  └─────────┘ └─────────┘ └─────────┘   │
│                        │  ┌─────────┐ ┌─────────┐               │
│   Princess · rose      │  │ Rainy   │ │Starlight│               │
│                        │  └─────────┘ └─────────┘               │
│                        │                                         │
│                        │  Changes save automatically.            │
└────────────────────────┴─────────────────────────────────────────┘
```

- **Looks** shows the three built-ins and the user presets, each with an Apply action and a Delete action for user looks. A name field and Save button create a preset from the current look.
- **Outfit** shows the five full-body outfits.
- **Accessories** has four labelled rows: Bow, Hat, Glasses, Wand.
- **Theme** shows six color swatches.
- Chips use swatches and labels rather than per-item thumbnails; the live preview is the feedback. `aria-pressed` marks the current item. Arrow keys move within a group, Enter/Space selects.
- The preview is a 300×340 canvas running the same `BuffyCharacter.draw` as the overlay, in a slow idle bob. The Idle/Reading/Coffee/Stretch chips force a preview pose without changing the overlay. The caption below names the current outfit and theme.
- The window closes with its title bar or Escape.
- When the current sprite is a hatched image, a banner says the sprite replaces the built-in character and that outfits/hobbies are previews only. The preview still shows the built-in character so the wardrobe is not a dead end.
- All changes are applied immediately to the overlay and saved automatically. A failed save shows a short inline message; the change still applies for the session.

The tray and context menu replace the four old wardrobe submenus with **Wardrobe…** and **Surprise me**. The rest of the menu stays as it is.

### 3. Rendering architecture

The character art moves out of `renderer.js` into `overlay/character.js`, a classic script exposing `window.BuffyCharacter`:

- `draw(ctx, { now, state, look, width, height, customImage, cursor, hobby, hobbyStartedAt })` draws the shadow, body, wardrobe, props, and ambient effects. The overlay's drag trail stays in `renderer.js`.
- `paletteFor(theme)` returns the hue and accent values the overlay uses for thinking dots and the keyboard.
- `PET_SCALE`, `drawHeart`, and `drawSparkle` are exposed for the overlay's effects.

`index.html` loads `character.js` before `renderer.js`. `wardrobe.html` loads `character.js` before `wardrobe.js`. The overlay keeps its bubble, session rail, drag, cursor, and IPC logic; `renderer.js` loses roughly a thousand lines of drawing code.

Layer order inside `draw`:

1. floor shadow
2. cloud head
3. headphones
4. pixel face
5. hat
6. tiara
7. bow
8. outfit body
9. outfit shoes
10. hobby prop
11. hands and wand
12. ambient effects

The `princess` outfit keeps today's theme-tinted blue fabric. The four new outfits use their own fabric palettes with theme-colored accents, so "rainy" stays yellow and "starlight" stays dark across themes. Hats, bows, and glasses anchor to the cloud head, which does not change shape, so they align across every outfit.

If `customImage` is present, `draw` paints the image and skips every procedural layer and hobby prop. This preserves today's hatch behavior exactly.

### 4. Idle life

A new classic script, `overlay/hobbies.js`, exposes `window.BuffyHobbies` with a pure scheduler:

- `createHobbyScheduler({ random, idleHobbies, sleepAfterMs, firstDelayMs, gapMs })`
- `update(now, { hovered, busy })` returns the active hobby or `null`.
- `activity(now)` resets the idle clock and clears the current hobby.
- `isAsleep(now)` reports the sleep state.
- `configure(patch)` updates `idleHobbies` or `sleepAfterMs`.

Hobbies:

| Id | Duration | Pose |
| --- | --- | --- |
| `reading` | 20s | holds an open book, eyes down, page flips every ~4.5s |
| `coffee` | 16s | holds a mug with steam, sips every ~6s |
| `stretch` | 7s | arms up, eyes closed, a small yawn and sparkles |

Timing defaults:

- First hobby after **8 seconds** of idle.
- A **9-second** gap between hobbies.
- Sleep after **120 seconds** since the last activity, configurable from 30 seconds to 10 minutes.
- A hobby in progress finishes before sleep; sleep never cuts a page-turn or a sip in half.
- The next hobby is chosen randomly and never repeats the previous one immediately.
- Hovering over the pet counts as activity: it clears a hobby in progress and prevents a new one from starting. Moving away starts the 8-second delay again.
- Any agent event, click, wave, drag, or wake clears the hobby immediately. `needs-you`, `working`, `thinking`, `error`, `done`, `wave`, `wake`, `sleepy`, and `offline` always win over a hobby.
- Hobbies are cosmetic. They do not add XP, change mood, increment counters, or send events.
- With `idleHobbies: false`, she keeps the old quiet idle and still sleeps after the configured window.

The scheduler is a plain classic script so it can be unit-tested by loading it into a Node `vm` context. The renderer owns `requestAnimationFrame`, passes `performance.now()`, and decides `busy` from the daemon state.

The reading and coffee poses share the existing hands: the prop is drawn before the hands so the hands sit on the book or mug. The wand is hidden during a hobby. The stretch pose reuses the wake-stretch arc.

### 5. Settings and tray

`config.json` gains an `overlay` block:

```json
{
  "overlay": {
    "idleHobbies": true,
    "sleepAfterMs": 120000
  }
}
```

`overlay/settings.cjs` owns the defaults and clamping so the main process and tests agree. `sleepAfterMs` is clamped to 30,000–600,000 ms. The main process reads `overlay` at startup, sends it to the renderer on load and whenever it changes, and writes only the `idleHobbies` key when the tray checkbox is toggled, preserving every other config key.

The tray/context menu adds **Idle hobbies** as a checkbox. There is no UI for `sleepAfterMs`; it is documented as an optional config value.

### 6. Persistence, migration, and failure behavior

- On startup, `normalizeWardrobe(readJson(WARDROBE_FILE, {}))` runs before the first broadcast.
- A v1 file `{ bow, hat, wand, theme }` maps to v2 with `outfit: 'princess'`, `glasses: 'none'`, and `wand: true → 'star'`, `false → 'none'`. The other four values are preserved exactly when valid.
- The migrated object is written back as v2 on the first save; reading it is idempotent.
- Writes use a temporary file plus rename, so a crash cannot leave a half-written wardrobe.
- Unknown item IDs fall back per slot to the catalog default. Malformed presets are dropped. A corrupt file falls back to defaults without preventing the overlay from starting.
- A failed write returns an error to the wardrobe window; the in-memory look and overlay still update for the session.
- No new state file is added. Hobbies live in `config.json`; presets live in `wardrobe.json`.

### 7. Shipping v1.1.0

- Bump `package.json` and `package-lock.json` to `1.1.0`. `src/config.js` already derives `VERSION` from `package.json`.
- Update `README.md`: status, wardrobe window, presets, hobbies, sleep timing, `overlay` config, `wardrobe.json` shape, and the custom-sprite limitation.
- Update `docs/index.html`: v1.1.0 download links, wardrobe card, idle-life card, and new screenshots.
- Update `overlay/onboarding.html` to say "Buffy 1.1" and mention the wardrobe window.
- Capture new screenshots of the wardrobe window, reading, and coffee. Keep them in `docs/shots/`.
- Run `npm test`, `npm run dist:win`, and `npm run smoke:packaged` locally. Tag `v1.1.0` and let the release workflow build macOS and Linux.
- Verify the published release has all four installers, checksums, and `latest*.yml` with `version: 1.1.0`.
- Verify the Pages site and the README download links return 200.
- Repeat the isolated updater check from v1.0.1: install the published 1.0.1, let it download 1.1.0, confirm the installed `app.asar` is 1.1.0, and confirm the relaunched process has `--updated`.

Signing remains optional and unchanged. If no signing secrets are configured, the builds stay unsigned.

## Decisions I made (check these)

1. Five outfits, four accessory slots, six themes. No color wheel or pattern editor.
2. A standard framed window, not a transparent overlay panel.
3. Built-in looks plus up to 12 user presets; presets store a full look, not a live link.
4. Reading, coffee, and stretch; reading and coffee get the most time.
5. Sleep moves from 30 seconds to 120 seconds so hobbies have room, and is configurable.
6. Hobbies are cosmetic only, with no XP or mood effects.
7. Hobbies and outfits do not apply to hatched custom sprites in this release.
8. The tray's four wardrobe submenus are replaced by **Wardrobe…** and **Surprise me**.
9. The character renderer is extracted into a shared classic script; no bundler or new dependency.
10. The wardrobe window previews hobbies, but the overlay's hobby schedule remains automatic.

## Review focus

These are the failure modes most likely to bite a real user, and each one needs a test or a deliberate check in the implementation plan:

- A v1 wardrobe with a lavender bow, party hat, wand on, and mint theme must survive migration exactly.
- A hand-edited `wardrobe.json` with an unknown outfit or preset must fall back without a blank pet or a crashed overlay.
- A hatched custom sprite must render exactly as it does today; the wardrobe window must explain why outfits do not appear on it.
- A hobby must never play during `needs-you`, `working`, or while the pointer is over the pet, and an interrupting event must clear it on the next frame.
- Sleep must not cut off a hobby mid-animation, and a hobby must not keep her awake forever.
- Rapid outfit clicks must leave the overlay and the preview in sync and must not corrupt the save file.
- A theme change must apply to both the overlay and the open wardrobe preview at the same time.
- The packaged app must include the new scripts and window assets and still pass the smoke test on all three platforms.
- The release feed must advertise 1.1.0 and the installed 1.0.1 must upgrade and relaunch.

## Proposed implementation sequence

1. Extract `character.js` from `renderer.js` with no visual change; update `index.html`; extend the smoke check.
2. Add the catalog, v2 normalization, migration, and pure wardrobe operations with tests.
3. Build the wardrobe window shell, preload, IPC, and tray entry; wire the existing choices into it.
4. Draw the new outfits, hats, glasses, wands, and themes; add the preview controls.
5. Add built-in and user presets, save/apply/delete, and "Surprise me".
6. Add the hobby scheduler, settings plumbing, sleep timing, and unit tests.
7. Draw reading, coffee, and stretch; integrate interruption and the preview poses.
8. Update README, site, onboarding, screenshots, and version; run the full local checks.
9. Tag and publish 1.1.0; verify the release feed, assets, site, and an isolated 1.0.1 → 1.1.0 updater run.

## What is left to the builder

- Exact draw geometry for the new outfits and props, checked against screenshots at the overlay's 300×330 size.
- The precise wording and visual polish of the wardrobe window within the existing onboarding language.
- Whether each new outfit needs one or two extra accent details to read clearly at 100% scale.
- The final preset names and the exact screenshot set for the site.
- Whether the 120-second sleep feels right in daily use; the value is configurable if it does not.
